I spent some time recently working on [a tool that I use to sync markdown notes](https://github.com/joshcanhelp/mdsync) from an [Obsidian](https://obsidian.md) vault (bunch of interlinked Markdown files, if you're not familiar) to a repo I'm working on (like the directory that you're reading this in, most likely). I used it as an excuse to try out Claude Code in earnest, defaulting to asking an agent instead of writing the code myself. That experience was quite eye-opening and I actually enjoyed the process, despite a [strong initial bias against it](https://www.joshcanhelp.com/ai/) (I'll write more about that transformation the future). Once I "finished" (is software ever actually finished?) that project, I immediately started thinking about this one. 

I spent the last ~9 months working on an AI security product that scrapes APIs, stores the resulting JSON, and then enriches and processes the resulting data in a way that is (hopefully) useful for security and IT professionals. If you're at all familiar with this PDPL project, that should sound quite familiar.

Those two things together started to get me really excited about this project again and what could be possible with a jobs-worth of new experience and a significant increase in how much software I'm able to write within a given period of time. In my head, it's helping my flip around my anxiety around how much more powerful AI is going to make big tech. We're also able to use this tech to fight that power and take our data back, if not entirely then enough that it's worth the time and thought. 

So I've been thinking about what I actually want this system to be capable of. At first it was built to gather and combine data, focused on building up a timeline. I wanted everything I had out there in the cloud to be available locally and in chronological order. The next step was to take that data and output files based on combinations of the data I was collecting.

And I got there! I currently have many, many Markdown files locally that represent all of my Strava workouts since ... *checks search* ...  2012. That's an achievement and I'm happy to get there. 

But ...

The last ride I have in markdown is 2024. That's not accurate. Is the process still running? TBH, I don't know, I haven't checked it in a while. Looks like it was October of last year. And the last ride I have JSON for is around that same time. GitHub has a bunch of stuff as well but everything stopped October 15th and I don't know why. I tried to run the script that runs all APIs and there are lots of errors going on there. Not sure why it hasn't run lately. 

All that to say: there is a big observability problem here. It would be great to get some kind of notice that the system is not functioning properly. Relying on cron is not the best way to do this cross-platform, I need something that runs cheaply in the cloud. Also, relying on file paths to the configuration and secrets and JSON output is not great. And that's just fixing what already exists. 

On top of that, I have a bunch of things I want this system to be able to do, some of which I've been thinking about for a long time and some that just recently came to mind. 

- It needs a dashboard of some kind that shows the state of things (queue, logs, etc)
- It needs key management accessible on the internet
	- https://github.com/Infisical/infisical
- It needs to store the JSON in something S3-compatible (with some way to back that up locally)
	- https://garagehq.deuxfleurs.fr
- This needs to be piped to Postgres/DB in the simplest way possible
	- https://github.com/duckdb/pg_duckdb
- The source data should be cloud *or* local. If I post something to ... somewhere (I don't do that much), I want to write it locally and send it up, rather than syncing it down.
- One of the biggest things: I want to be able to delete things from the cloud once I have a local/S3 copy. This would mean the state of the "entity" (like a post, workout, etc.) would be managed in PDPL. 
- The API jobs need to be able to "fan out" and get additional data based on data that was gathered before.
- Some clients will need to consume the data in order to make their own files so there needs to be some kind of API there.
- This API could also be used to receive webhooks (like new Strava workouts) and other requests that need to make it into the system, including *from* certain clients (like an iCloud sync of some kind)

And then *that's it*, nothing else. Oh and it has to be dead-simple. And bulletproof.

So I look at that and I think "holy shit, that's a lot" and it definitely is by any measure. But the fact that this work can move faster and happen at times when maybe I have enough focus to direct an agent and review for the less impactful tasks makes me feel more hopeful that this is possible.
