
I had an epiphany last night (short for: realized something obvious that had eluded me for a while). I was thinking about omitting/including fields, translating/modifying fields ... when it occurred to me that the raw data should stay generally as-is and any new fields or data translation would go into a new table, not modify the existing one. So, if we wanted to mess with data from a certain table, we need to just describe the new table and not worry about converting types in the same table.

Back to tables ... I've been trying to think of a good way to represent this translation and I think the original concept for recipes makes sense to keep pursuing so I'll keep pushing on that. In short:

- New tables are defined atomically in YML/JSON. These always need to be user-provided since the tables and transformations depend on what you're pulling down. This need to be API capable at some point in the future but I don't need to worry too much about it.
- The order of operations here is
	- Select the data we want from the existing data. 
		- Validation can decide if this is possible or not
- We need to know:
	- The name of the existing table
	- The fields we're getting from that table
	- The transformations we're doing on those fields
	- The name of the new table
- I don't really want anyone to have to know all the naming conventions being used here, like needing to know that the source and the dir/endpoint are connected with underscores. 

Side note ... I keep getting stuck thinking about this portion of the system because of all the different ways this can run, as well as the ways it has to run. This can run locally or in the cloud but certain extractions can be local (imports and anything else that relies on files be present). Then, once extracted, the data can kind of end up anywhere (it's just JSON so could be stored on a box, in the cloud, synced locally, all of the above). Then you have all the the user-defined stuff that needs to get piped into the script for the transformation and output. That also depends on where you want things to be stored (local DB, cloud DB, both). Same with output at some point, output could be local or calling APIs. I'd like to spend some time thinking through all of these use cases and at least making sure I'm thinking about interfaces (not writing them all but just making sure they can be extended as folks need).
